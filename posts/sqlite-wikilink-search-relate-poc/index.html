그래프 DB를 도입하기 전에, SQLite 검색에 위키링크를 붙여봤다

Nov 27 2026-11-27T16:28:31+09:00 by abruption
7 min

“HTTP 502 장애의 복원 절차는 어디 있지?”라는 질문을 합성 운영 문서로 만든 검색 실험에 넣었다. 전문 검색으로는 장애 보고를 찾을 수 있었지만, 실제 복원 절차는 상위 다섯 개에 없었다. 장애 보고에서 원인 기록으로, 거기서 다시 복원 절차로 이어지는 위키링크를 따라가니 찾을 수 있었다.

개인 Obsidian 볼트는 Markdown을 원본으로 두고 SQLite FTS5로 제목과 본문을 검색한다. 인덱서를 만들 때 위키링크도 방향이 있는 관계로 저장해 뒀다. Relate를 살펴보면서 궁금했던 건 검색과 경로 탐색을 그래프 DB에 함께 맡기면 이 질문을 더 잘 처리할 수 있느냐였다. 그걸 보려면 우선 SQLite에서도 같은 링크를 따라가 봐야 했다.

두 엔진에 같은 질문을 던졌다

합성 한국어 운영 문서 40개에 방향 링크 32개를 넣었다. 검색어가 겹치는 문서를 더해 1,440개 문서와 링크 4,232개로 늘린 데이터셋도 만들었다. 두 저장소의 문서 ID와 링크 집합이 원본과 일치하는지 확인했다. 질문은 12개였다. 10개에는 정답 문서를 지정했고, 그중 8개에는 기대하는 두 단계 경로도 정해 뒀다. 나머지 2개는 관련 문서가 없는 질문이었다.

질문에서 뽑은 단어는 두 엔진에 같은 OR 조건으로 넣었다. 링크 결합 검색은 각 엔진의 전문 검색 순위에서 상위 두 문서를 골라, 각 문서에서 나가는 링크를 최대 두 단계까지 따라갔다. SQLite에서는 FTS5의 BM25 점수와 재귀 CTE를 썼고, Relate에서는 Cypher의 SEARCH와 [:LINKS_TO*1..2]를 썼다. 이후에는 두 엔진에 같은 규칙을 적용했다. 출발 문서의 순위와 링크를 따라간 횟수로 후보를 정렬하고, 같은 문서가 여러 경로로 나오면 앞선 경로만 남겨 상위 다섯 개를 비교했다.

두 단계만 따라가도 놓친 문서를 찾았다

두 데이터셋에서 모두 전문 검색의 상위 다섯 개에 정답을 넣은 질문은 10개 중 6개였다. 링크를 함께 탐색하자 두 엔진 모두 10개를 찾았다. 기대한 두 단계 경로까지 일치한 질문은 문서 40개에서 8개 중 6개, 1,440개에서 8개 중 7개였다. 관련 문서가 없는 두 질문에는 결과가 나오지 않았다. 같은 정렬 규칙을 적용한 이 실험에서는 상위 다섯 문서의 순서와 경로도 같았다.

Linux ARM64에서 Python 3.12.3, SQLite 3.45.1, Relate 1.3.0으로 실행했다. 각 엔진은 별도 프로세스에서 디스크 저장소를 읽기 전용으로 열었다. 워밍업 뒤 검색 방식별로 360회씩 세 번 직렬 실행했다. 표의 각 분위수는 세 실행에서 나온 해당 값의 중앙값이며, 시간에는 Python의 결과 처리도 포함된다.

출발 문서 ID를 고정하고 링크 탐색만 별도로 비교하니 두 엔진 모두 기대한 경로 8개를 찾았다. 이때 p50은 SQLite 0.010ms, Relate 0.129ms였다. 이번 구성에서는 전문 검색을 포함했을 때 지연 차이가 더 컸다.

링크만으로 해결하기 어려운 경우도 있었다. 합성 문서에 복구를이 들어 있으면 두 엔진 모두 복구를로는 찾았지만 복구로는 놓쳤다. 검색어 때문에 출발점부터 놓치면 링크를 따라갈 기회도 사라진다.

웹 검색에는 SQLite와 위키링크를 붙였다

운영 웹 검색에는 기존 전문 검색 결과 아래에 연결 문서 목록을 추가했다. 검색 상위 두 문서에서 출발해 위키링크를 최대 두 단계까지 따라가고, 경로에 있는 모든 문서를 사용자가 읽을 수 있는지 검사한다. 이미 전문 검색으로 찾은 문서는 연결 목록에서 빼고, 나머지는 최대 다섯 개까지 경로와 함께 보여준다. 연결 조회가 실패해도 전문 검색 결과는 계속 쓸 수 있다. 이 동작은 타입 검사와 격리 회귀 테스트 76개로 확인했다.

측정에는 합성 문서와 한 번에 한 건씩 도는 조회를 사용했다. 운영 문서에서의 검색 품질, 동시 요청, 캐시가 비어 있는 첫 조회는 따로 측정해야 한다. 지금 필요한 관계는 문서에 이미 남겨 둔 위키링크였다. 앞으로 관계 유형이 늘어 SQL로 관리하기 어려워지거나, 실제 문서에서 검색 품질 차이가 확인되면 Relate를 다시 검토할 생각이다.
