# 포스트 작성 스타일

## 기본 방향

- 기술 설명보다 먼저 실제로 어떤 문제가 생겼는지 쓴다.
- 가능하면 `문제 발생 → 처음 세운 가설 → 확인 과정 → 실제 원인 → 현재의 판단` 순서를 따른다.
- 경험하지 않은 수치, 실행 결과, 실패 원인을 그럴듯하게 보태지 않는다. 확인되지 않은 내용은 추정이라고 밝힌다.
- 독자에게 정답을 가르치는 문서보다, 다른 개발자에게 작업 과정을 설명하는 회고에 가깝게 쓴다.

## 문체

- `-했다`, `-이다`, `-같다`를 기본으로 하고, 필요한 곳에만 `-해보면`, `-그냥`, `-한참` 같은 구어적인 표현을 섞는다.
- 억지로 반말이나 `-해요`체로 바꾸지 않는다. 구체적인 상황과 개인의 판단이 구어체의 핵심이다.
- `이 글에서는 ... 정리한다`, `핵심은 세 가지다`, `결과적으로 ... 제공한다` 같은 정형 문장을 반복하지 않는다.
- 모든 문단을 결론으로 닫지 않는다. 여전히 불편한 점, 버릴 수 있는 선택지, 나중에 바꿀 가능성도 남긴다.
- 코드·명령어·로그·실패한 시도는 가능한 한 보존하고, 그 앞뒤에 왜 실행했는지와 무엇을 보고 판단했는지를 쓴다.

## 작성 전 확인

- 현재 저장소와 실제 운영 워크플로우가 글의 내용과 맞는지 확인한다.
- 외부 정책·라이브러리·서비스 동작처럼 바뀔 수 있는 내용은 확인 시점과 범위를 적는다.
- 글을 고칠 때는 작업 브랜치를 사용하고, `bundle exec jekyll b`와 `bash tools/test.sh`를 실행한다.
